# Pllum Connect protocol 1

The contract between Pllum and this helper. Pllum refuses any other protocol version.

**Transport.** One JSON object per line, UTF-8, `\n`-terminated, at most 16 MiB a line. Pllum writes requests to the helper's standard input; the helper writes responses and events to its standard output and nothing else. Standard error is never read for content. End of input means "shut down": the helper disconnects and exits within 5 s.

**Shapes.**
- Request: `{"id":"<string>","method":"<name>","params":{…}}`. IDs are Pllum's, unique while the helper runs. Every method but `hello` carries `"network"` in its params.
- Response: `{"id":"…","result":{…}}` or `{"id":"…","error":{"kind":"<kind>"}}`. Responses may come in any order.
- Event: `{"event":"<name>","network":"…",…}`, with no `id`.
- Times are integers in Unix milliseconds, in fields ending `Ms`. Cursors are opaque strings. Unknown fields are ignored on both sides.
- The first request is `hello` `{"protocol":1,"storeKey":"<64 hex>","app":"<Pllum version>"}` → `{"protocol":1,"version":"<helper version>","commit":"<git SHA>","networks":["whatsapp"]}`. Any other version → error `outdated`, and Pllum stops the helper. Before `hello`, every other request is `badRequest`.

**Error kinds** (the only values of `kind`): `badRequest`, `unknownMethod`, `unknownNetwork`, `notConnected` (not signed in), `offline` (signed in, no connection now), `notFound`, `notOnNetwork` (a `beeper:` line), `refused` (WhatsApp turned it down before it was sent; safe to retry), `unclear` (it may have happened), `rateLimited`, `tooLarge`, `mediaGone`, `unsupported`, `storeKey`, `outdated`, `timeout`, `internal`, and, for networks signed in through a website, `checkpoint`, `pinWrong`, `pinLimit` (see Additions below).

**States** (`status` and the `state` event): `notConnected`, `linking`, `connecting`, `catchingUp`, `live`, `offline`, `reconnectNeeded`, `outdated`, `banned`.

**Chat:** `{"id","kind":"single"|"group","title"|null,"phone"|null,"lastActivityMs","lastMessageID"|null,"lastFromMe","unread","muted","readOnly","participants":[{"id","name"|null,"phone"|null,"isSelf"}],"historyFromMs"|null,"historyComplete"}`. `title` is the group's subject, else WhatsApp's name for the person (his phone's contact name, then their push name), else null. `participants` holds at most 64. `muted` is read against the clock: a mute his phone set until a time reads muted until then and unmuted after, and the helper sends `changed` when it lapses.

**Message:** `{"id","chatID","senderID","senderName"|null,"fromMe","timeMs","text"|null,"kind":"text"|"photo"|"video"|"voiceNote"|"sticker"|"file"|"notice","hidden","deleted","edited","replyTo"|null,"media":[{"kind","width"|null,"height"|null,"hasFile"}],"reactions":[{"emoji","senderID","fromMe"}],"seenMs"|null}`.

**Methods:**

| Method | Params (besides `network`) | Result |
|---|---|---|
| `hello` | `protocol`, `storeKey`, `app` | `protocol`, `version`, `commit`, `networks` |
| `shutdown` | — | `{}`, then exits |
| `status` | — | `state`, `selfChatID`\|null |
| `login` | `method`: `"qr"`, or `"session"` with `session: {"<cookie name>": "<value>"}` (every value a string; an empty or mistyped `session` is `badRequest`) | `{}`; progress comes as `qr` and `state` events (for `session`, `state` events only; a failure is `state` `notConnected` with a `kind`) |
| `cancelLogin`, `logout` | — | `{}` |
| `nudge` | — | `{}`: reconnect now if not connected (after sleep) |

| `chat` | `chatID` | `chat: Chat`\|null |
| `messages` | `chatID`, `before`?, `limit` (≤200) | `items: [Message]` oldest first, `hasMore`, `oldestCursor`?. A page that reaches the oldest stored line (`hasMore` false) of a chat that is not `historyComplete` also asks the network to fetch older lines, if it can: at most once per chat per 10 s, never while one is running; the answer does not wait for it |

| `sendStatus` | `messageID`, or `clientID` (the key a `send` was made with) instead | `state`: `sending`\|`sent`\|`failed`\|`unknown`, `kind`?, `lineID`?; asked by `clientID`, also `messageID` of the send the key names (none, and `unknown`, when it names none). Both or neither is `badRequest`. `lineID` is the ID of the line the send became, once the network has it and when it differs from the sent ID; only on `sent` |
| `react` | `chatID`, `messageID`, `emoji` (`""` removes), `transactionID` | `{}` |
| `markRead` | `chatID`, `through`? (a message ID; null = newest incoming) | `{}` |
| `markUnread` | `chatID` | `{}` |
| `setMuted` | `chatID`, `muted` | `{}` |
| `media` | `chatID`, `messageID` | `path` (a file under `connect/media/`) |
| `import` | `beeperChatID`, `chatID`\|null, `chat: {kind, title?, phone?}`, `messages: [ImportMessage]`, `replaces`? | `added`, `matched`, `skipped` |
| `beeperChats` | — | `map: {beeperChatID: chatID}` |
| `lineIDs` | `beeperIDs: [String]` (≤1000) | `map: {beeperID: lineID}` |
| `counts` | — | `chats`, `messages`, `imported`, `matched`, `unplacedChats`, `oldestMs`\|null, `nearMisses` (optional) |

| `chatByParticipant` | `participantID` | `chat: Chat`\|null: the one-to-one with that person (never a group, never an unplaced chat; the most recently active if several). For Instagram it also accepts the person's FBID (Beeper's form), translated through the people the helper has seen |
| `encryptedHistory` | — | `state`: `noBackup`\|`needsPIN`\|`restored`\|`skipped`; `unsupported` for a network with none |
| `restoreHistory` | `pin` (a string; `""` skips; missing is `badRequest`) | `{}`; errors `pinWrong` (with `attemptsRemaining`?), `pinLimit`; `unsupported` for a network with none |

`counts.nearMisses` is a measure, a count only: per network, the Beeper-only lines (`source` beeper) in placed chats that have a direct line on the same side (`fromMe`) within 2000 ms, none of which has the same content as the Beeper line under the matcher's `MatchKey` rules. It reads text to compare and returns a number, never text, IDs or JIDs, and changes nothing about matching. A helper that does not send it is read as 0.

`ImportMessage`: `{"beeperID","networkID"|null,"fromMe","senderID"|null,"senderName"|null,"timeMs","text"|null,"kind","hidden","deleted","replyToBeeperID"|null,"media":[{"kind","width","height"}],"reactions":[{"emoji","senderID","fromMe"}]}`. A null `chatID` makes or extends the unplaced chat `unplaced:<beeperChatID>`; `replaces` names an unplaced chat whose rows are dropped once this placed import has them. An exact-time, one-to-one twin counts as matched: a copy whose text differs (a mention, say) from a direct line that carries no Beeper ID, on the same side at the same non-zero `timeMs`, when each is the only such line at that time in the chat and both have text or share a media kind.

**Events:** `session` `{session}`: the full named cookie set of a network signed in through a website, sent when it differs from the last one sent (or the one `login` was given), at most once a minute, and never a set missing a required cookie; `state` `{state, kind?}`; `qr` `{code, expiresMs}`; `history` `{chats, messages, done}` (counts while the link-time sync arrives; `done` after a 100% batch or 120 s with none); `changed` `{}` (something to re-read; at most one per 500 ms per network).

**Additions for networks signed in through a website** (Instagram, Messenger). All are additive, so the protocol stays 1; Pllum and the helper ship together.

- `hello`'s `networks` lists `"instagram"` and `"messenger"` when the helper runs them.
- `signIn`: Pllum shows `url` in a web view with `userAgent`, waits for an address matching `donePattern` (a regular expression on the full URL), reads the `required` and `optional` cookies of `cookieDomain`, and sends them as `login` with `method:"session"`. The helper presents the same user agent to Meta, so the window and the helper look like one browser.
- Error kind `checkpoint`: Meta wants him to confirm it is him (a challenge, checkpoint or consent page). It is also a `state` `kind`, on state `reconnectNeeded`. The helper makes no further requests until he signs in again.
- How a `login` with a session ends: `badRequest` at once (and `state` `notConnected` `badRequest`) when a required cookie is missing or empty, before anything is asked of Meta; else `{}`, then `state` `connecting`, and `catchingUp` when the socket subscribes, `live` at its first update or 60 s on. A checkpoint is `reconnectNeeded` with kind `checkpoint`, an ended session `reconnectNeeded`, a suspended account `banned`; Meta's error 1357053 and a redirect loop count as an ended session. Any other failure is `notConnected` with its kind: a `nudge` retries `offline` and `timeout` with the cookies held; `rateLimited` is retried by the helper when the block ends; anything else waits for a new `login`. A failed inbox reload after Meta asks for a resnapshot is `offline` (with `rateLimited` while a block is in force), retried the same way. The cookies are held in memory only (the latest rotated set once Meta rotates them), so Pllum sends `login` on every start; with the client's saved state for that session the helper resumes from the saved sequence ID, with no request before the socket, and loads the inbox otherwise. A checkpoint, ended session or suspension is kept in the store (its kind and a SHA-256 of the required cookies of every version of the session sent to Pllum, never their values): at start, and on a `login` matching any of them, the helper reports that state again and asks Meta nothing; a `login` with a different session (a new sign-in) clears it. A rate limit is kept too (its end and its count), so a restart neither asks before the block ends nor starts the doubling over.
- Instagram's IDs: a chat is its thread key in decimal (for a one-to-one, the other person's FBID); a line is Meta's message ID (`mid.$…`) unchanged; a participant is an Instagram user ID (IGID). `selfChatID` is null.
- Instagram's writes (every one through the pace, as are the reads they need: the thread's IDs, an upload, a media fetch and an expired photo's refresh; while a block is in force each is refused with its kind). `send` needs state `live`, `catchingUp` or `offline` (else `notConnected`) and answers at once with `otid:<offline threading ID>`; the send goes in the background, in order. A file is uploaded first, then any text goes as its own message, then the photo or video (JPEG, PNG, MP4 or QuickTime, up to 16 MB; anything else is `unsupported`): two lines, as Instagram shows them, and `lineID` is the file's. `sendStatus`: `sent` with `lineID` (Meta's message ID) once Meta answers or the send's echo arrives; `failed` `refused` when nothing reached Meta (never asked, or the connection was never made) or Meta said no (an error answer, a 4xx, a checkpoint, an ended session, a ban, a rate limit); `failed` `unclear` when the text of a text-and-file went and the file did not, and then a `send` with the same `clientID` (Try again) is the same send and sends the file alone; `sending` while it may have reached Meta (no answer in time, a connection broken after it was made, a 5xx, an answer that could not be read); a send still `sending` when the helper starts is `unknown` from then on and is never sent again (a later echo still makes it `sent`). No write is asked again after Meta answered or may have: the two send mutations are asked once (the library's own retries are switched off for them), and an upload is one request. A repeated `send` with the same `clientID` gives the same ID and sends nothing, unless the first failed. `react` with an empty emoji removes his reaction; a `transactionID` already held sends nothing; a `beeper:` line is `notOnNetwork`. `markRead` names the newest unread line at or before `through`. `markUnread` is kept in the helper's store only (Instagram has no such write). `setMuted` mutes for ever or unmutes. `media` fetches a photo or sticker once from its CDN address; an address the CDN no longer takes is refreshed with one page of history, then the answer is `mediaGone`.
- Error kinds `pinWrong` and `pinLimit` are `restoreHistory`'s only. `pinWrong` may carry `attemptsRemaining`, an integer: `{"id":"…","error":{"kind":"pinWrong","attemptsRemaining":2}}`. No other error carries it.
- `status` may carry `encrypted`: `notRegistered`\|`connecting`\|`live`\|`failed` (Messenger only; a network that has no end-to-end encryption leaves it out).
- Messenger (in progress, branch `messenger`): `signIn` is facebook.com's page. `login` with a session loads the messages page once and connects the main (lightspeed) socket; on its first connect, as mautrix-meta's connector does, the helper registers Pllum as a Messenger device for the encrypted chats (once, ever: kept in `messenger/device.db` in the data folder and reused by every later sign-in), connects the encrypted socket, looks for the PIN backup of his encrypted history, lists every folder of his inbox and fetches the recent history of its unencrypted threads. The listing (at the first sign-in, and every sign-in with `--gate`) pages each folder a Messenger client shows with `FetchThreadsTask`: every parent the messages page names (the inbox is -1; Marketplace and communities have their own) and every folder thread a listing shows, in sync group 1 (the inbox), and under the parents the messages page names in sync group 95 (message requests), until Meta says the folder has no more, its oldest thread stops moving, a thread over 365 days old (not with `--gate`), or 40 pages; 120 pages in all. Then, at the first sign-in (never with `--gate`), each chat active in the last 90 days that has an unencrypted thread and a line of it held gets up to 5 pages of its older lines (`FetchMessagesTask`, whose page comes back on the main socket; one not back in 20 s is passed over). The first sign-in's work is resumable: each folder's progress, the listing, each chat's pages and the backfill are kept in the store as they go, so a rate limit, Meta pushing back or a quit carries on at the next sign-in rather than starting again, and a folder or chat that fails with an error of its own (or a page the helper cannot read) is passed over. A history page is anchored on the oldest line Meta has given of the thread, else the oldest of its lines held, and a thread with neither is never asked; a page that never comes, fails to parse or times out in the library, does not reach back past what is held, or answers with an existing range that does not end the history holds that chat for 6 hours (kept across restarts), during which `messages` at its oldest line asks nothing. Every request goes through the pace. Groups without encryption are chats keyed by their thread key; an encrypted one-to-one is `<FBID>@msgr` and an encrypted group `<id>@g.us`; a one-to-one without encryption (thread key = their FBID) is an alias of `<FBID>@msgr`, never a second chat, and so is an older thread a hybrid pointer names. Their lines (Meta's message IDs), reactions, read receipts, mutes and people are written as they come from the messages page, the pages and the main socket; spam (filtered requests) and folders are never chats. The encrypted chats' lines come on the encrypted socket under whatsmeow's message IDs, in `<FBID>@msgr` or `<id>@g.us` (a new person's first one makes their chat): text, photos, videos, voice notes, stickers and files (the message kept as `raw` to fetch the file later), replies, view-once, locations, contacts, polls and calls as labelled text, reactions, edits and revokes of the lines they name, and anything else as a hidden notice; each is written before whatsmeow acks it, so one not kept for a passing reason (a store error, or a sign-in that has ended) comes again at the next connect, while one that can never be kept (the store refuses it, or reading it fails) is acked and kept as a hidden notice under its ID where it can be. A message the helper could not decrypt is acked by whatsmeow before the helper sees it, so it never comes again that way. A read receipt marks his lines seen, his own from another device moves his read marker, and a message the helper could not decrypt is a hidden notice under its ID (counted as `liveUndecryptable`) that the message, arriving again readable, takes over. Once his history is restored, his backup is read for the encrypted chats: at the first restore (or the first sign-in after it; never with `--gate`) up to 2 pages of 50 lines for each encrypted chat active in the last 90 days, newest chat first, 100 pages in all, each chat's progress and the whole kept in the store so a stop resumes and nothing is asked twice; each line is stored with source `sync` under the same ID it has live, so a line restored and also received live is one row. Every backup request that reached Meta counts towards that cap, failures included. A page of the backup that does not reach back past where it was asked from, cannot be read or cannot be decrypted, or a request Meta fails, holds that chat's backup for 6 hours, then 24 hours, then 7 days each time after (kept across restarts); two failed requests in a row, across any chats, pause the whole backup the same way and end the first restore's read, so a failure of the whole backup is asked at most twice there. Meta saying a chat has no backup marks it done; Meta saying the backup is gone (no longer available, a different backup) drops the history device, so `encryptedHistory` is `needsPIN` again and nothing of the backup is asked until `restoreHistory`. Reading to a chat's oldest line asks at most 100 pages of the backup a day across every chat. `messages` reaching a chat's oldest line asks for one more page of its backup while the backup has more, then one more page of its unencrypted thread; a chat is `historyComplete` once each of its sides (its unencrypted thread, if any, and its backup, if it is encrypted) has no more, and a chat with neither asks nothing. A checkpoint, an ended session or a suspension is kept in the store, so a restart or the same cookies sent again asks Meta nothing until a new sign-in; a rate limit is kept to its end. State is `connecting` until both sockets are up, then `live`; `offline` with kind `unsupported` while the main socket is up but the encrypted one is down (reconnecting, or ended by Meta; once Meta has ended it, no history of any chat is asked until a new sign-in), and `offline` while the main socket reconnects; Meta suspending the encrypted device (a temporary ban) is `banned` and logging it out is `reconnectNeeded`, each kept as the main socket's are, so nothing is asked until he signs in again; `status` carries `encrypted`: `live` while the encrypted socket is up, `connecting` while a sign-in is in force and it is not, `failed` once Meta ended the encrypted session (nothing re-registers or reconnects it on its own) or its registration failed, and `notRegistered` with no sign-in in force; a main socket Meta refuses as unauthorized is `reconnectNeeded`. A registration that fails after Meta was asked (its answer lost, or the device not saved) is `notConnected` with kind `unclear`: signing in again is not the fix, and a later sign-in in the same helper registers the same keys again rather than a new device. `encryptedHistory` and `restoreHistory` work as above: `restoreHistory` takes a six-digit PIN (anything else is `badRequest`, and Meta is asked nothing), needs the encrypted socket up (else `notConnected`), asks Meta once and never again on its own, and keeps nothing of the PIN; no backup is `notFound`, an enrolment Meta refused is `refused`, and one whose answer never came is `unclear`. The library retries reads on a 5xx, a 429 or a dropped connection, but never the two PIN steps or the device enrolment, so a PIN attempt is spent at most once. Every write is `unsupported` for now.
- `gateCounts` (hidden): answered only by a helper started with `--gate`, else `unknownMethod`. Params `network` (`messenger`) → counts only: `loaded`, `groups`, `listPages`, `listComplete`, `listCapped`, `encryptedPointers`, `encryptedThreads`, `encryptedOneToOnes`, `registered`, `registerMs`, `mainConnected`, `e2eeConnected`, `e2eeFailed`, `historyState` (`encryptedHistory`'s words, or `""` before it has looked), `restoredMessages`, `liveEncryptedReceived`, `liveUndecryptable`, and a breakdown of every thread listed (an older thread and its encrypted one apart), each a map of fixed words to counts: `byFolder` (Meta's folder names the library knows, `noFolder`, `otherFolder`), `byType` (`oneToOne`, `group`, `encryptedOneToOne`, `encryptedGroup`, `marketplace`, `communityGroup`, `folder`, `otherType`), `bySyncGroup` (`1`, `95`, `otherGroup`), `folderStops` (how each folder's listing ended: `complete`, `yearReached`, `capped`, `failed`) and `olderThanYearByType`; and the numbers `olderThanYear` (last active over 365 days ago), `otherParents` (parents besides the inbox), `inOtherParents` (threads under them), `noActivity` (listed with no last activity), and `oneToOneChats` and `groupChats`: the distinct chats the listed threads make after aliasing (`<FBID>@msgr`, encrypted or not; unencrypted groups and `<id>@g.us`), the numbers to compare with Beeper's one-to-ones and groups. `listPages` counts every folder's pages. With `--gate`, a restored history is sampled once: one page of the newest encrypted one-to-one, decrypted and counted, never kept.
- Pace: the helper leaves a random 2 to 4 s between requests to Meta. After `rateLimited` it makes none for 15 minutes, then 30, 60, 120 and 240 on each further one (a success starts over); after `checkpoint`, `reconnectNeeded` or `banned` none until a new `login`. A success during a rate-limit block does not end it. One exception is the library's: when Meta answers a mutation (a send, reaction, read receipt or mute) with "please reload the page" (1357004), it reloads the inbox (at most once per 15 minutes) and asks that mutation once more, outside the pace; Meta refused the first ask, so a message still goes once.

**Go interface each network implements** (`internal/network`):

```go
type Network interface {
	Name() string                                     // "whatsapp"
	Start(ctx context.Context) error                  // connects if signed in; returns at once
	Status() Status                                   // State, SelfChatID
	Login(ctx context.Context, p LoginParams) error // LoginParams{Method string; Session Session}
	CancelLogin()
	Logout(ctx context.Context) error
	Nudge()
	Send(ctx context.Context, m Outgoing) (messageID string, err error)
	SendState(messageID string) SendState
	React(ctx context.Context, chatID, messageID, emoji, transactionID string) error
	MarkRead(ctx context.Context, chatID, through string) error
	MarkUnread(ctx context.Context, chatID string) error
	SetMuted(ctx context.Context, chatID string, muted bool) error
	Media(ctx context.Context, chatID, messageID string) (path string, err error)
	Stop()
}
```

A network may also implement these optional interfaces, which `server` finds with a type assertion (`internal/network`):

```go
type SignInPager interface{ SignIn() meta.SignInPage }
type OlderPages interface {
	FetchOlder(ctx context.Context, chatID string) (added int, err error)
}
type EncryptedHistory interface {
	HistoryState() string
	RestoreHistory(ctx context.Context, pin []byte) error
}
type Gate interface{ GateCounts() any } // gateCounts, with --gate only
```

A network without one answers `unsupported` to its method (`OlderPages` is simply not called). `FetchOlder` sends `changed` itself when it adds lines or finds the start of a chat.

`Session` is `map[string]string` whose `String`, `GoString` and `Format` all give `[session redacted]`, so no `fmt` verb prints a cookie.

Reads (`chats`, `chat`, `messages`, `search`, `findChats`, `chatByParticipant`) and the Beeper calls (`import`, `beeperChats`, `lineIDs`, `counts`) are answered by `server` from `store` for every network; a network only writes into the store.
